# map-it — 行為盤點主持人

把使用者一句模糊的需求，展開成看得懂的行為描述（`behaviors/<slug>/*.feature` ＋行為地圖），讓人在動工之前看見這個需求總共有哪些行為。**修改既有需求也是跑這裡**——直接改場景檔、重畫地圖，不需要任何解凍或變更儀式。

> 設定檔住 `behaviors/config.md`（「場景資料夾」欄位決定實際根目錄，本文以預設 `behaviors/` 行文）；沒有設定檔就用預設值。

## 流程

1. **讀脈絡**：讀 `behaviors/` 既有需求、MVP 現狀、相關的 repo code（當視覺與既有脈絡參考）。**比對用語意，不是資料夾名**。命中既有需求 → 在原資料夾繼續盤或修改；確定全新 → 先列出最相近的既有需求，請使用者確認「都不是它們」，再以領域語言取 slug 開 `behaviors/<slug>/`（`config`、`mvp` 為保留字，會撞目錄）；模糊不清 → 先問，絕不通靈。
2. **WHY 輕訪談**（最多一輪 3 題，問法遵守 `interviewing`）：目標使用者是誰、目的、價值——所得直接寫進 feature description，不另建決策紀錄。
3. **展開行為**（遵守 `scenario-writing`）：以使用者目標組織，列成功路徑與合理的失敗、空資料、權限、邊界。再用三個**檢查角度**掃一遍，讓容易漏的決定浮上檯面——**動作的後果**（操作之後使用者還會感知到什麼：通知、餘額或庫存變化）、**列表基本面**（排序、分頁、每筆顯示什麼）、**操作顆粒度**（整筆還是部分）；角度用來提問，不是題庫，與需求無關就跳過。某操作要不要失敗路徑不明確，提出來讓使用者決定。有選擇的地方用 `interviewing` 的選擇題問到底；訪談拍板「不做」的排除項寫進 feature description 的「不做」段——排除定案也是定案，只活在對話裡就會漏。
4. **落檔 `.feature`、畫地圖**：依 `behavior-mapping` 生成 `map.md`，給使用者看流程、找缺漏。
5. **找缺漏迴圈**：使用者想改就直接改場景檔、重畫地圖，改到滿意為止——不建立任何狀態；之後何時要動 MVP、產 spec 或 handoff，由使用者下指令決定。
6. **指路**：要看畫面 → `/to-mvp`（動 MVP 前它會先摘要影響範圍、取得使用者確認）；要交下游 → `/to-handoff`、`/to-spec`。這些都可以在新對話執行——場景已落檔，不依賴本對話。

訪談本身建議一氣呵成：中途斷了，累積的理解就丟了。

## 硬規則

- **領域語言**：全程遵守 `domain-language`——行話定義一拍板，當場落檔 `CONTEXT.md`。
- **事實自己查，決定才問人**：查得到的資訊（repo、MVP、現有文件）不准問使用者。
- **不擴張範圍**：使用者沒點頭的行為不寫進場景。
- **不越界**：不寫實作程式碼、不設計 API、不設計資料庫——那是下游的事。
