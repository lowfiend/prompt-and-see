# to-handoff — 真相 → 交付

交付＝**整合原型（脈絡）＋該需求的標註（改哪裡）**：下游打開 `behaviors/mvp/` 走整個流程，照標註定位本需求動了哪幾頁的哪些狀態——如同拿到整份設計稿加一層「這次改這裡」的標記，而不是一張去脈絡的單功能畫面。本 skill 生成需求資料夾裡的 `handoff.md`——它是**導讀（manifest）**，不是內容的複本：真相看同資料夾的 `*.feature`、圖看 `map.md`、畫面走 `behaviors/mvp/`、標註看 `coverage.md`。

> 設定固定在 `behaviors/config.md`；其「場景資料夾」欄位決定實際根目錄（本文以預設 `behaviors/` 行文）；沒有設定檔就用預設值。

## 前置檢查

- `map.md` 必須 `狀態: 已凍結`，否則停。
- **新鮮度**：依 `coverage.md` 檔頭逐檔記錄的「相對路徑＋SHA-256」，對本需求各 `.feature` 逐檔重算比對；任一不符、檔案有增減、或 `coverage.md` 不存在 → 先重跑 `/to-mvp`（全量重生），再生成導讀，並在變更摘要說明。**過期的產物是謊言，不准交付。**
- **完整性**：本需求 `coverage.md` 有任何「缺頁」或「無法觸發」→ 停止交付——回 `/to-mvp` 補生成或 `/remap` 補行為。普查級完整性是本方法的核心承諾，不完整的原型不准出門。「未操作驗證」不擋，轉錄進變更摘要。**其他需求**的缺口不擋本次交付，但列入 `handoff.md` 的「已知缺口」——整夾出門，下游有權知道哪裡還沒到位。

## handoff.md 的內容（導讀五件事）

1. **版本與變更摘要**：檔頭標版本；與上一版的行為差異（新增／修改／移除了哪些場景），讓下游一眼辨識新鮮度。
2. **關鍵決定與依賴**：轉錄地圖檔頭的關鍵決定與依賴——下游不用先開圖就知道「為什麼長這樣」「要先有什麼」。
3. **本次改動標註**：**摘要**本需求涉及哪幾頁、coverage 是否完整、任何未操作驗證或已知缺口；逐節點的詳細標註**直接指向同資料夾的 `coverage.md`**，不複製整張表——導讀不是 coverage 的複本，兩份一起膨脹就是漂移的溫床。
4. **交付清單（manifest）**：逐項列出——場景檔、`map.md`、`coverage.md`、涉及的頁面檔；`config.md` 有設定設計系統文件就一併列入。清單以 config 的實際設定為準——**缺任何一件列出的項目，即為不完整交付**。
5. **角色使用說明**：
   - **交 QA**：場景即測項，逐條驗（假設／當／那麼＝前置／操作／預期）；發現場景漏了行為，**不得只補在測試裡**——回報行為負責人，回場景檔 `/remap` 後重新生成，測項才算數。
   - **交 UIUX review**：原型頁面是「產出」，review 是**審查把關，不是重刻**；純視覺意見回殼層來源（宿主樣式／設計系統），涉及行為的意見回場景檔討論。
   - **交 RD**：照地圖施工，地圖上沒有的行為不要做；**文案與版面的唯一參照是整合原型的頁面**（場景釘死的文字原樣在頁面上；場景沒釘死的中性文案以**目前原型頁面**為參照，不自行發明——某段文字必須固定，回 `/remap` 寫進場景）；想加行為先回場景檔（`/map-it` 或 `/remap`）。

## 鐵律

- 檔頭聲明：「本檔為重新生成的產物，手改無效；要改行為請改場景檔。」
- **不內嵌場景全文與地圖**——同資料夾就有活的真相，內嵌快照只會與它漂移打架。
- 單向生成：只讀場景／地圖／原型，絕不反向修改它們。
- **傳遞方式**：同 repo 協作給 `behaviors/` 路徑即可——原型與標註都在裡面。跨頻道傳送（config「交付模型」為可攜單包，或收件者無 repo 存取）＝打包 zip：本需求資料夾＋**整個 `mvp/` 資料夾**（含入口頁與 `assets/`），**保留 `behaviors/` 之下的相對目錄層級**——整夾打包讓連結閉包天然成立：共享頁上其他需求的按鈕連出去的頁面也都在包裡，不會斷鏈。清單列出的設計系統文件一併打包，並在 manifest 註明「原型含其他已凍結需求的行為」。
