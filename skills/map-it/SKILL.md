# map-it — 行為盤點主持人

目標：把使用者一句模糊的需求，變成一份**凍結的行為真相**（`behaviors/<slug>/*.feature` ＋行為地圖），讓所有人在動工之前，就看見這個功能做出來總共有哪些行為。

> 設定固定在 `behaviors/config.md`；其「場景資料夾」欄位決定實際根目錄（本文以預設 `behaviors/` 行文）；沒有設定檔就用預設值，並提醒可跑 `/setup-prompt-and-see`。

## 流程

1. **定位**：檢查 `behaviors/` 是否已有相關的需求資料夾。**比對用語意，不是資料夾名**——讀各資料夾 `map.md` 檔頭（狀態＋關鍵決定＋依賴）與場景標題來判斷。四分支：
   - 命中既有且**已凍結** → 停，指路 `/remap`（變更有自己的護欄：範圍鎖定、防夾帶、變更紀錄——不繞過）。
   - 命中既有且**還在討論中** → 在該資料夾繼續盤（上次沒盤完）。
   - 確定全新 → **先列出最相近的既有功能，請使用者確認「都不是它們」**，確認後才以領域語言取 slug 開 `behaviors/<slug>/`。slug 是功能一輩子的身分證：不掛版本號、不加編號，異動不改名（禁 `-v2`、`-new` 這類後綴）；**`config`、`mvp` 為保留字，不得作 slug**（會與設定檔、整合原型撞目錄）。
   - 模糊不清 → 先問使用者釐清，絕不通靈。
2. **WHY 輕拷問**（最多一輪 3 題）：目標使用者是誰？商業價值？要驗證什麼假設？問法遵守 `interviewing`。行為盤點途中發現 WHY 有漏（選擇題答不出來是因為目標不明），允許回頭補問，不硬撐。
3. **攤行為樹**：以畫面為骨架，列出每個畫面的按鈕與操作、按了會發生什麼、失敗與例外路徑（無資料、無權限、載入失敗、狀態衝突）。粒度遵守 `scenario-writing`（按鈕級）。有選擇的地方用 `interviewing` 的選擇題問到底。
4. **產出場景檔**：使用者拍板後，依 `scenario-writing` 寫入 feature 檔。
5. **產出行為地圖**：依 `behavior-mapping` 生成 `map.md`。
6. **找碴迴圈**：請使用者看地圖找碴。任何改動：先改場景檔 → 重新生成地圖 → 再請使用者看。重複到使用者說「凍結」。
7. **凍結**：在 `map.md` 檔頭標 `狀態: 已凍結 <日期>`，回報統計（幾個功能檔、幾條場景、幾條失敗路徑）。
8. **指路**：告訴使用者下一棒——要看畫面 `/to-mvp`、要交下游 `/to-handoff`、要轉規格 `/to-spec`；之後要改行為用 `/remap`。這些都可以在**新對話**執行（真相已落檔，不依賴本對話）。

## 硬規則

- **領域語言**：全程遵守 `domain-language`——用詞沿用 `CONTEXT.md`，訪談中行話定義一拍板就當場落檔。
- **事實自己查，決定才問人**：查得到的資訊（repo、現有文件）不准問使用者。
- **不擴張範圍**：使用者沒點頭的行為不准寫進場景。
- **不越界**：不寫實作程式碼、不設計 API、不設計資料庫——那些是下游的事。
- **凍結後要改**：唯一路徑是回來改場景檔，並重新生成所有產物。
