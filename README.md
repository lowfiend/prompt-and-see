# prompt-and-see

> **Prompt and pray? No — prompt and see.**
> 在 AI 動工之前，看見它要做的每一個行為。

## 為什麼存在

四個每天都在發生的翻車現場，每個都有對應的藥。

### 翻車 #1：看不見行為

> [!CAUTION]
> AI 給了做法、你點了頭，做出來才發現——沒權限的人看得到按鈕、失敗時畫面一片空白。驗收條款是「抽查」不是「普查」，沒被寫下的行為全靠實作者腦補，**落差就住在腦補裡**。

> [!TIP]
> **解藥：`/map-it`**——訪談把行為攤成普查級的場景檔（每顆按鈕的成功與失敗至少各一條），畫成一張行為地圖，你**看圖找碴**到滿意才凍結。訪談紀律（`interviewing`）、場景紀律（`scenario-writing`）、畫圖紀律（`behavior-mapping`）三顆零件都為這站服務。

### 翻車 #2：看不見畫面

> [!CAUTION]
> 行為對了，但體驗要親眼看到才能判斷；而且沒有人幫錯誤狀態畫畫面——「系統忙碌中」長什麼樣，往往上線那天才第一次有人看到。

> [!TIP]
> **解藥：`/to-mvp`**——照地圖生成整合原型：**每個節點、包括每一條失敗路徑，都有看得到、點得動的畫面**，而且是在整個 app 的脈絡裡走出來的，附覆蓋對照表，漏做哪個狀態一眼看見。

### 翻車 #3：文件腐化成謊言

> [!CAUTION]
> 需求改了，規格、圖、交接文件沒人記得跟著改。三個月後，沒有人敢說哪份文件是真的。

> [!TIP]
> **解藥：單一真相、單向生成**——手寫的只有場景檔；地圖、原型頁面、交付導讀全部從它生成。**改真相走 `/remap`，產物過期就重生**，每份產物檔頭都寫著「手改無效」。交付用 `/to-handoff`：版本、變更摘要、交付清單，下游一眼辨識新鮮度。

### 翻車 #4：同一個詞，各說各話

> [!CAUTION]
> 「有效訂單」含不含退貨處理中？「使用者」指買家還是後台管理員？同一個詞每次討論重新吵一遍，AI 也跟著每次換一種講法。

> [!TIP]
> **解藥：`domain-language`**——詞的定義一拍板就寫進 `CONTEXT.md`（詞＋定義＋禁用詞），之後全專案的人、文件、AI 用同一套詞，用錯會被糾正。

---

這四個痛，有三個正是 BDD 二十年前的創始承諾（Specification by Example、Living Documentation、Ubiquitous Language）——過去它靠 Cucumber 落地，門檻卡在工程端，最該用它的人反而用不動；**我們用 agent 把它兌現到不會寫程式的人手上**。

這套 skills 只管「**動工之前**」：凍結後的場景檔是唯一真相，下游要什麼（整合原型、SpecKit／OpenSpec 規格、交付包）都從它生成——我們不跟下游工具競爭，我們是它們的上游。

## 主流程一句話

**`/map-it` 盤行為 → 凍結 → `/to-mvp` 看畫面 → `/to-handoff` 交出去；要改就 `/remap`。**

## Skills

**使用者呼叫**（你打指令才會動，負責主持流程）

| skill | 做什麼 |
|---|---|
| `/setup-prompt-and-see` | 每個 repo 跑一次：場景放哪、語言、設計系統、殼層來源、下游格式、UI 設計 skill、交付模型 |
| `/map-it` | 從一句需求開始：WHY 輕拷問 → 攤行為樹 → 產場景檔 → 畫地圖 → 找碴 → 凍結 |
| `/remap` | 對已凍結的真相做變更：鎖定範圍 → 改場景 → 重生地圖 → 重新凍結＋變更紀錄 |
| `/to-spec` | 凍結真相 → 下游規格格式（SpecKit／OpenSpec／自家格式），行為照搬、技術缺口明示 |
| `/to-mvp` | 凍結真相 → 整合原型：一畫面一頁面檔，合併所有已凍結需求的行為（含失敗狀態）＋覆蓋對照表＋入口頁 |
| `/to-handoff` | 生成導讀：整合原型當脈絡＋覆蓋對照表當標註交付；版本＋變更摘要＋交付清單＋角色說明 |

**模型自動呼叫**（agent 情境符合就會自己用；你也可以手動呼叫）

| skill | 做什麼 |
|---|---|
| `interviewing` | 訪談紀律：一輪問完、附推薦答案、只問決定不問事實、查證派 sub-agent 不阻塞 |
| `scenario-writing` | 場景紀律：中文 Gherkin、按鈕級粒度、成功失敗成對、跨功能界線、BDD 弱項聲明 |
| `behavior-mapping` | 地圖紀律：畫面＝節點、失敗標紅、圖不比真相多；場景一改立刻重生——過期的地圖是謊言 |
| `domain-language` | 領域語言紀律：讀寫 `CONTEXT.md` 詞彙表（詞＋定義＋Avoid），全專案用同一套詞 |

## behaviors/ 結構

```
behaviors/
├── config.md                ← ⚙️ 設定（/setup 生成；「config」「mvp」為保留字）
├── mvp/                     ← ⚙️ 整合原型：一夾＝一個可走的原型（/to-mvp 全量重生）
│   ├── index.html           ← 入口頁：按功能＋按畫面反查
│   ├── assets/              ← 殼層：共享 CSS／JS／字型
│   └── <畫面>.html          ← 一畫面一頁：合併所有已凍結需求的行為（含失敗態）
└── <slug>/                  ← 需求資料夾＝功能身分證（＋設計系統文件）
    ├── *.feature            ← ✍️ 行為真相（全 repo 唯一手寫）
    ├── map.md               ← ⚙️ 行為地圖（檔頭：狀態＋關鍵決定＋依賴＋變更紀錄）
    ├── coverage.md          ← ⚙️ 覆蓋對照表：地圖節點 × 頁面＋狀態＝本需求的標註
    ├── handoff.md           ← ⚙️ 交付導讀（不內嵌全文——真相就在同一夾）
    └── spec/                ← ⚙️ 下游規格翻譯件
```

- **slug 是功能一輩子的身分證**：技術重構不動這裡；行為異動原地 `/remap`；只有新舊並存的新概念才開新資料夾。禁 `-v2`、`-new` 後綴——版本活在檔頭變更紀錄，不活在資料夾名。
- ✍️ 手寫的只有場景檔；⚙️ 其餘全是單向生成的產物——手改無效、過期即重生。

## 安裝

把 `skills/` 底下的資料夾複製到目標專案的 `.claude/skills/`：

```bash
cp -r skills/* <你的專案>/.claude/skills/
```

然後在專案裡跑一次 `/setup-prompt-and-see`。

## 接力方式

skills 之間不自動串接——每站做完由**你**決定下一棒。接力棒是**落檔的產物**，不是對話：

- **必須同一個對話一氣呵成**：`/map-it`（或 `/remap`）的拷問 → 攤行為樹 → 找碴 → 凍結。中途斷了，訪談累積的理解就丟了。
- **凍結之後隨時可開新對話**：`/to-mvp`、`/to-spec`、`/to-handoff` 只依賴凍結的 `behaviors/`，不依賴之前聊了什麼。
- **下游實作（RD）必開新對話**：交付的整合原型與標註已自足，帶著舊脈絡反而污染。

## 硬規則（整套 skills 的憲法）

1. **場景檔是唯一手寫真相**（`behaviors/<slug>/*.feature`）；地圖與一切下游文件都是單向生成的產物。
2. **粒度＝按鈕級**；資料級細節留給下游規格。
3. **凍結後要改，回來改場景檔**，全部重新生成——不做小補丁、不做狀態機。
4. **不替聰明的 agent 做事**：下游（QA、RD、UIUX）拿到的是可靠的行為真相，怎麼用是他們的專業；他們發現場景有漏，必須繳回場景檔。
