# architecture-governance — 模組化紀律

模組化是**決定**，不是預設。簡單專案保持簡單——拆模組要有真實的結構壓力，不是為了資料夾好看。

> 宿主專案的 CLAUDE.md 與慣例檔是最終權威；本紀律是預設值，與宿主慣例衝突時以宿主為準。

## 什麼時候值得拆

- **強訊號**：多個能獨立演化的產品區塊；多品牌／白牌要在共用行為上覆寫；同一功能要被多個 app 重用；多團隊需要明確的所有權界線。
- **弱訊號（不足以動手）**：「以後可能會長大」、想要乾淨的資料夾、架構圖看起來比較專業。
- **反訊號**：單一產品面、單一團隊、流程緊耦合、沒有現實的重用或覆寫需求。

訊號弱就選簡單分層；訊號強才刻意拆，並把界線寫下來。

## 分層責任

- **shared／base**：設計系統、原語、工具、共用契約——提供**能力**。
- **feature**：業務 UI、狀態、領域行為——提供**領域**。
- **app**：路由、組裝、環境設定、最終覆寫——**唯一的組裝點**。

## 鐵則

- **依賴方向**：shared 不依賴 feature；feature 不隨便橫向依賴 feature；app 永遠是最後的組裝點。
- **抽象要養活**：一個抽象要服務多於一個真實需求；只有一個實作的 registry／覆寫系統是過度設計。
- **覆寫 opt-in**：預設零設定能跑；真有品牌、平台、app 級差異才開覆寫口，不為「說不定哪天要」到處加間接層。

## 過度設計自省（收尾必查）

- 有沒有模組找不到獨立存在的理由？
- shared 層有沒有藏業務邏輯？
- 有沒有只有一個實作的 registry 或 config 系統？
- 這次的界線是降低了複雜度，還是把複雜度改藏進間接層？
