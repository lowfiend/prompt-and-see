# to-mvp — 真相 → 畫面

讀取**所有已凍結需求**的場景檔與行為地圖，全量生成**整合原型**到 `behaviors/mvp/`：一個畫面節點＝一個頁面檔，每頁合併所有已凍結需求在該畫面的行為。讓人在寫任何正式程式之前，就能走著整個流程，親眼看到並操作每個功能。

> 設定固定在 `behaviors/config.md`；其「場景資料夾」欄位決定實際根目錄（本文以預設 `behaviors/` 行文）；沒有設定檔就用預設值，並提醒可跑 `/setup-prompt-and-see`。

## 前置檢查（不通過就停）

- 本次要求生成的需求，`map.md` 檔頭必須是 `狀態: 已凍結`。未凍結 → 停下來告訴使用者先用 `/map-it` 走完找碴與凍結。**不在未凍結的真相上蓋房子。**
- 發現舊制產物 `behaviors/<slug>/mvp/` → 告知使用者已改為整合原型，全量生成成功後刪除舊產物。

## 產出結構

`behaviors/mvp/` 整個資料夾＝一個完整可走的整合原型（「mvp」為保留字，slug 不得使用）：

```
behaviors/mvp/
├── index.html      ← 入口頁（本 skill 生成，見下）
├── assets/         ← 殼層：共享 CSS／JS／字型
└── <畫面>.html     ← 一個畫面節點＝一個頁面檔
```

## 全量重生（唯一模式）

**每次執行都讀取全部已凍結需求，重新生成整個原型**——沒有增量模式：

- 全量自然清掉被移除、改名的舊頁與任何手改。「生成物手改無效」的意思就是：**下次全量生成會覆蓋**。
- 未凍結的需求不合併；入口頁標「討論中、尚無畫面」。
- **先在臨時目錄完成全量生成與基本驗證（每個地圖節點有畫面、失敗態可觸發、連結不斷）；成功後才替換既有 `mvp/`，失敗保留舊原型。**
- skills 不自動串接：`/remap` 之後原型即視為待重生，重生由使用者跑本 skill。

## 頁面合併規則

- **一個頁面檔＝該畫面節點在所有已凍結需求地圖上行為的聯集**，含每條失敗態。畫面身分＝`CONTEXT.md` 詞彙表的畫面名稱（命名紀律見 `behavior-mapping`——同一實體畫面在所有地圖必須同名）。
- **檔名**：由畫面名稱轉成安全的小寫 kebab-case（例：訂單列表頁 → `order-list.html`）；`index`、`assets` 不得使用；兩個畫面轉出同名 → 停下請使用者裁決，**不自行加序號**。入口頁與 coverage 引用同一份檔名。
- **矛盾即停**：兩個需求對同一畫面的同一操作寫出無法以條件區分的不同結果 → 停下指出矛盾，請使用者回場景檔裁決（`/remap`），生成器不准挑邊。

## 殼層（assets/）

依 `behaviors/config.md` 決定殼層來源，優先序：

1. config 的**殼層來源**指定了宿主 app 的 **build 產物**路徑 → 從 build 產物萃取編譯後 CSS、字型檔、靜態 chrome 進 `assets/`。**誠實聲明：萃取給的是「樣式保真」，元件行為仍是本 skill 從場景重刻的**——不得宣稱「複用宿主 app」。
2. config 有 **UI 設計 skill** → **明確呼叫它**取得設計系統，生成殼層。不碰運氣等自動觸發。
3. config 有**設計系統文件**（如 `DESIGN.md`、元件庫規格）→ 對齊它生成殼層。
4. 都沒有 → 中性樣式殼層，不自創視覺語言。

**字型 self-host 進 `assets/fonts/`**（可用 subset 減肥）；禁 CDN——可攜單包複製不了 CDN 資源，且原型須可離線開啟。字型檔取不到（下載失敗、授權不明）→ 退回系統字型堆疊、在覆蓋對照表備註，不擋生成。

## 引用白名單

頁面只准引用 `behaviors/mvp/` 內部（含 `assets/`）；禁止引用 `mvp/` 外任何路徑與任何外部資源。

## 覆蓋規則（核心）

**地圖上有幾個節點，原型就要有幾個看得到的狀態**——包括每一條標紅的失敗路徑：

- 畫面節點（📄）→ 一個頁面檔
- 按鈕節點（🔘）→ 真的能點，點了走場景寫的那條線；線跨到別的畫面就真的連到那一頁
- 失敗／例外狀態（❌）→ 可觸發或可切換檢視（例如用假資料開關模擬「查無結果」「服務錯誤」）

每次全量生成，**為每個已凍結需求**產出 `behaviors/<slug>/coverage.md`（生成物，檔頭聲明手改無效，並記生成日期，且**逐一記錄該需求各 `.feature` 的相對路徑與 SHA-256**——`/to-handoff` 依同一路徑逐檔重算，判斷需求是否後來變過）。表格給人看：

| 地圖節點 | 頁面／狀態 | 已覆蓋 | 已操作驗證 | 備註 |
|---|---|---|---|---|

缺頁或無法觸發的節點一眼看得見——這張表就是本需求交付時的**標註**，`/to-handoff` 據以把關。

- **整檔重生，不留歷史**：`coverage.md` 每次都只從目前的 `map.md` 與本次全量生成結果重新推導、**整檔覆蓋**——禁止追加或保留歷史列。節點新增就加列、移除就刪列、改名就換列、畫面合併就依目前地圖重排；歷史交給 Git。
- **只放這些**：地圖節點、對應頁面／狀態、是否覆蓋、是否操作驗證、必要的短備註，加上檔頭的生成日期與逐檔 SHA-256。場景全文、截圖、長篇 review 意見、變更紀錄、重複的地圖內容一律不放——它是**當前狀態的生成報表**，不是流水帳。

## 外部入口

- 來源是 `behaviors/` 內其他功能、且該畫面已在原型裡 → **直接連到那一頁**。
- 來源功能尚未凍結、原型裡沒有那一頁 → 明確 stub：「模擬：來源功能〈X〉尚未凍結，暫無頁面」。
- 來源是未納入盤點的既有系統 → 最小假入口，標注「模擬：入口行為屬 `<來源>`」。

## 入口頁

本 skill 生成 `behaviors/mvp/index.html`（生成物，手改無效），兩個分區：

- **按功能**：每個需求資料夾一列——名稱、狀態（討論中／已凍結＋日期）、場景數／失敗路徑數、涉及頁面的連結。
- **按畫面反查**：從所有功能地圖反推「畫面 → 涉及的功能」索引，連到對應頁面檔。同一畫面掛太多功能＝結構腐化的警報。

## 驗證

有瀏覽器工具就逐頁逐狀態截圖，對照地圖驗版面、顯隱、RWD；沒有就在覆蓋對照表「已操作驗證」欄註明未驗證（不擋交付，`/to-handoff` 會轉錄給下游）。

## 硬規則

- **不發明行為**：場景裡沒有的按鈕、流程一律不出現在頁面上。導覽與入口頁是鷹架、不是行為，也只准列真實存在的頁面。想到「應該還要有」的東西 → 提出來，走回場景檔（那是 `/map-it`／`/remap` 的事）。
- **文案分兩級**：場景釘死的文字**照抄**；場景沒釘死、畫面又必需的文字（欄位標籤、佔位字、提示語）可補**中性文案**，但不得藉補文案夾帶新行為。中性文案不承諾跨重生不變——**某段文字必須穩定，就回場景檔把它釘死（`/remap`）**，場景才是真相。
- **假資料要一眼看得出是假的**（例如商品名用「範例商品 A」），避免被當成真實內容流出去。
- 原型是生成產物：場景改了就重跑本 skill 全量重生，不在頁面上手改行為。

完成後指路：下一棒通常是 `/to-handoff`（整合原型當脈絡、覆蓋對照表當標註交付）；看了畫面想改行為 → `/remap`。
