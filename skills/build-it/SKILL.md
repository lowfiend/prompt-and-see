# build-it — 領票施工主持人

本次只處理**一張票**：領票 → 施工 → 場景驗收 → 照實回報 → 停；不依賴任何對話歷史——一切輸入都是落檔（場景、spec、MVP）。下一張票由使用者決定（建議開新對話領：票的大小以一個 context window 為度，就是為此）。

> 設定檔住 `behaviors/config.md`（「場景資料夾」欄位決定實際根目錄，本文以預設 `behaviors/` 行文）；沒有設定檔就用預設值。

## 流程

1. **領票**：讀 `behaviors/<slug>/spec/spec.md` 的拆票節。先判斷哪些票已完成——查 git 歷史與宿主 tracker，判斷不了就問使用者；領一張 blockers 全完成的票，多張可領就取編號最前的（拆票按依賴序編號）。使用者指定就照指定；指定的票 blockers 未完成時，明說擋在哪並停止，不動工。
2. **讀契約**：票對應的場景＝驗收標準；技術決定節＝技術契約；`behaviors/mvp/` 對應頁面＝**畫面契約**——契約是 MVP 的**可見行為**，不是它的實作手法；畫面行為照 MVP，不重新發明，MVP 沒答的細節才自己補。
3. **盤慣例**：宿主 repo 的 CLAUDE.md、慣例檔、已安裝的紀律 skills、既有 code 都是事實——照著走，不重問。查不到又非決定不可的（元件化、文字資源機制這類），依 `interviewing` 一輪問完、每題附推薦答案；定案寫進宿主慣例檔（沒有就建，並在 CLAUDE.md 留一行指針）——一次定案，之後每張票免問。
4. **施工**：領票即動工，不另設前置確認——票就是同意過的範圍。過程中常跑型別檢查與相關測試。
5. **驗收＝場景**：專案能跑測試，就在技術決定節定好的測試接縫上**一場景一驗收測試**——測試讀起來就是場景；新驗收測試要**先於對應實作觀察紅燈**；行為已被既有實作滿足時，暫時破壞或反轉被測條件、確認測試會紅，還原後確認綠——沒有紅燈證據的測試不算驗收。測試資料由測試自己準備、不依賴預設示範資料。專案確實沒有可執行的驗收接縫時，退手動演示：逐場景列出操作步驟與結果。地基票沒有自己的場景——以自身可執行的工程檢查（建置、煙霧測試）驗收，下游場景事後承接；不得宣稱已被尚未施工的場景驗收。
6. **收尾**：全套測試最後跑一次；環境有 code review 工具就跑，沒有就自審一輪（正確性、票面符合度、慣例符合度）。宣稱已修的 finding，須附與該 finding 對應的測試或檢查結果；只列 diff 不算驗證。commit 前盤點 worktree——只 stage 本票的變更，動工前既有的未提交內容不納入、照實回報它們的存在；宿主慣例禁止自動 commit 就以宿主為準。**照實回報**：哪些場景過了、哪些沒過、用的是測試還是演示——不粉飾。

## 硬規則

- **行為主權**：場景沒有的行為不准發明；施工中發現行為缺口或場景矛盾 → 停下，指引使用者回 `/map-it` 討論，不在 code 裡自行決定。
- **單向**：絕不反向修改場景檔、地圖與 spec 的行為節；技術決定要改、或與環境事實衝突做不了 → 指引回 `/to-spec` 重新定案，不擅自推翻。
- **一次一張票**：沒把握在一個 context window 內做完，停下回報、建議拆票，不硬吃。
