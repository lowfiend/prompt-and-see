# prompt-and-see

> **Prompt and pray? No — prompt and see.**
> 在 AI 動工之前，看見它要做的每一個行為。

## 為什麼存在

四個每天都在發生的翻車現場，每個都有對應的藥。

### 翻車 #1：看不見行為

> [!CAUTION]
> AI 給了做法、你點了頭，做出來才發現——沒權限的人看得到按鈕、失敗時畫面一片空白。沒被寫下的行為全靠實作者腦補，**落差就住在腦補裡**。

> [!TIP]
> **解藥：`/map-it`**——訪談把需求展開成場景檔（成功路徑、合理的失敗與空狀態不能漏），畫成一張行為地圖，你**看圖找缺漏**，想改就直接改。訪談紀律（`interviewing`）、場景紀律（`scenario-writing`）、畫圖紀律（`behavior-mapping`）三顆零件都為這站服務。

### 翻車 #2：看不見畫面

> [!CAUTION]
> 行為對了，但體驗要親眼看到才能判斷；而且沒有人幫錯誤狀態畫畫面——「系統忙碌中」長什麼樣，往往上線那天才第一次有人看到。

> [!TIP]
> **解藥：`/to-mvp`**——照場景把 MVP 做成**免安裝、免編譯、直接打開就能操作**的靜態 HTML：失敗與空狀態都有看得到、點得動的畫面。動手前先摘要影響範圍，你點頭才改；想改就繼續下指令。

### 翻車 #3：文件腐化成謊言

> [!CAUTION]
> 需求改了，規格、圖、交接文件沒人記得跟著改。三個月後，沒有人敢說哪份文件是真的。

> [!TIP]
> **解藥：手寫的行為描述只有場景檔**——地圖與規格由它重生，交接導讀依當下場景與 MVP 現狀生成，過期就重生，檔頭寫著「手改無效」。MVP 是 code，原地增量維護；歷史、版本、diff 與還原交給 Git，不在 Markdown 記帳。

### 翻車 #4：同一個詞，各說各話

> [!CAUTION]
> 「有效訂單」含不含退貨處理中？「使用者」指買家還是後台管理員？同一個詞每次討論重新吵一遍，AI 也跟著每次換一種講法。

> [!TIP]
> **解藥：`domain-language`**——詞的定義一拍板就寫進 `CONTEXT.md`（詞＋定義＋禁用詞），之後全專案的人、文件、AI 用同一套詞，用錯會被糾正。

---

這四個痛，有三個正是 BDD 二十年前的創始承諾（Specification by Example、Living Documentation、Ubiquitous Language）——過去它靠 Cucumber 落地，門檻卡在工程端，最該用它的人反而用不動；**我們用 agent 把它兌現到不會寫程式的人手上**。

這套 skills 管「從一句需求到可操作的畫面」：場景檔描述行為，下游要什麼（規格、交接導讀）都從它生成——我們不跟下游工具競爭，我們是它們的上游。

## 主流程一句話

**`/map-it` 盤行為 → `/to-mvp` 做成可直接打開的靜態 MVP → 想改就繼續下指令 → 交接給 RD 用 `/to-handoff`；要讓 RD 領票施工，先 `/to-spec` 產拆票，再 `/build-it` 一票一票做。**

指令就是流程，對話中的確認就是授權——不需要被記錄成狀態。

## Skills

**使用者呼叫**（你打指令才會動，負責主持流程）

| skill | 做什麼 |
|---|---|
| `/setup-prompt-and-see` | 選填設定：場景資料夾、語言。沒跑也能用，各 skill 有預設值 |
| `/map-it` | 從一句需求開始：WHY 輕訪談 → 展開成功／失敗／邊界場景 → 產 `.feature` → 畫地圖給你看；改既有需求也是它 |
| `/to-mvp` | 照目前場景實作靜態 HTML MVP：有既有 MVP 就原地增量修改，沒有就建立；動手前先摘要、你同意才改 |
| `/to-spec` | 把當前場景生成極簡 spec：行為照搬＋技術決定訪談補齊＋拆票＋不做什麼。RD 有自己跑順的規格工具就不需要它——直接拿場景檔當輸入 |
| `/to-handoff` | 生成簡短交接導讀：場景與地圖路徑、MVP 入口與操作方式、已知事項；呼叫就生成，不設閘門 |
| `/build-it` | 領票施工（RD 端）：領一張 blockers 已完成的票，照場景與 MVP 施工，場景即驗收（能測則測、不行退演示），照實回報；一次只做一票，下一票建議開新對話 |

**模型自動呼叫**（agent 情境符合就會自己用；你也可以手動呼叫）

| skill | 做什麼 |
|---|---|
| `interviewing` | 訪談紀律：一輪問完、附推薦答案、只問決定不問事實、查證派 sub-agent 不阻塞 |
| `scenario-writing` | 場景紀律：中文 Gherkin、成功與合理的失敗／空狀態、跨需求界線、BDD 弱項聲明 |
| `behavior-mapping` | 地圖紀律：畫面＝節點、失敗標紅、圖不比場景多；場景一改立刻重畫 |
| `domain-language` | 領域語言紀律：讀寫 `CONTEXT.md` 詞彙表（詞＋定義＋Avoid），全專案用同一套詞 |

**施工紀律**（模型自動呼叫——給施工端的通用紀律；與上游流程互相獨立，裝在產品 repo 就會在寫 code 時生效，宿主慣例永遠優先）

| skill | 做什麼 |
|---|---|
| `architecture-governance` | 模組化是決定不是預設：拆不拆的訊號、分層責任、依賴方向鐵則、過度設計自省 |
| `ui-governance` | 語意元件優先（按後果判定）、有語意的視覺值走 token、重複模式先評估抽共用、只做行為所需的狀態、不遮內容、無障礙 |
| `i18n-governance` | 使用者可見文字不寫死、key 結構化命名、同義複用、動態文字用具名佔位符 |
| `image-governance` | 圖像資產命名結構化（含狀態變體）、共用／功能歸屬明確、路徑不散落——多資產或整批替換才集中 |

## behaviors/ 結構

```
behaviors/
├── config.md                ← 選填設定（/setup 生成；「config」「mvp」為保留字）
├── mvp/                     ← MVP：免安裝靜態 HTML，原地增量維護（位置固定）
│   ├── index.html           ← 唯一入口：直接打開就能操作
│   ├── assets/              ← 共用 CSS／JS／字型／圖片
│   └── *.html               ← 其他頁面
└── <slug>/                  ← 需求資料夾
    ├── *.feature            ← ✍️ 行為描述（手寫）
    ├── map.md               ← ⚙️ 行為地圖（由場景重生）
    ├── handoff.md           ← ⚙️ 交接導讀（依當下狀態生成）
    └── spec/                ← ⚙️ 極簡 spec（行為＋技術決定＋拆票＋不做什麼）
```

- ✍️ 手寫的行為描述只有場景檔；⚙️ 標記的是生成文件，手改無效——`map.md`、`spec/` 由當前場景整檔重生（spec 的技術決定與不做什麼兩節例外：以訪談定案為準，重生時沿用），`handoff.md` 依當下場景、MVP 與已知事項生成。
- **MVP 是 code，不是生成物**：人與 agent 都可維護，無關既有功能不因場景沒寫到而被刪；歷史交給 Git。
- slug 用領域語言取名（「訂單查詢」，不是「order-v2」）。

## 安裝

把 `skills/` 底下的資料夾複製到目標專案的 `.claude/skills/`：

```bash
cp -r skills/* <你的專案>/.claude/skills/
```

想調整預設路徑再跑 `/setup-prompt-and-see`（選填）。

## 接力方式

skills 之間不自動串接——每站做完由**你**決定下一棒；skill 不設流程閘門。接力棒是**落檔的產物**，不是對話：場景與地圖落檔後，`/to-mvp`、`/to-spec`、`/to-handoff` 隨時可在**新對話**執行。只有訪談本身建議一氣呵成——中途斷了，累積的理解就丟了。

## 硬規則（整套 skills 的憲法）

1. **場景檔是唯一手寫的行為描述**（`behaviors/<slug>/*.feature`）；地圖與規格由它整檔重生，交接導讀依當下現狀生成。它描述**目前需求**，不是整個 app 的總帳——場景沒寫到的既有功能不因此刪除。
2. **不發明未經使用者確認的業務行為**；合理的失敗、空資料與邊界狀態不能漏。
3. **MVP 永遠是免安裝、免編譯、直接打開就能操作的靜態 HTML**；有既有 code 就原地增量修改，無關功能保留。
4. **動手改 MVP 前，先摘要理解與影響範圍，使用者同意才改**——這個確認留在對話裡，不持久化成流程狀態；下一步由使用者下指令決定，歷史、版本、還原交給 Git。
