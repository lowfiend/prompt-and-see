# root-causing — 根治紀律

症狀消失不等於修好。一段修改若落在症狀顯現的地方，原因還在，它只是把問題推到下一次、下一台、下一個人身上。本紀律管的是**重現之後怎麼修**：通常接在 `reproducing` 把主張升級為已重現之後。

> 宿主專案的 CLAUDE.md 與慣例檔是最終權威；本紀律是預設值，衝突時以宿主為準。

## 何時進門

一段改動的理由是「修掉某個問題」，寫下去之前走這裡。審查時看到一段修法像在貼膠帶，也走這裡。

不走這裡的：新功能、重構、純風格調整——它們沒有「要修掉的問題」。

## 五步

1. **先說原因，一句話**：「被破壞的不變量是 ____」或「違反的設計前提是 ____」。這句話說不出來，就還沒到修的時候——回去找原因（要方法論，裝 Matt Pocock 的 `diagnosing-bugs`）。
2. **修在原因處**：改動的位置等於原因發生的地方。原因在 A、改動在 B，B 就是 workaround，不論它多有效。
3. **自檢**：下面任何一條中了，停下來重想：
   - 調 retry／timeout／backoff／輪詢間隔的數值，讓問題少發生
   - 針對某個輸入、某個環境、某台裝置開特例分支
   - catch 之後吞掉、回傳預設值假裝沒事
   - 加旗標關掉某條路徑
   - 多一份狀態去「同步」另一份，而不是讓兩份合一
   - 繞過既有設計硬接出結果（硬改）
   - 註解寫著「暫時先這樣」「之後再處理」
4. **workaround 只有兩種合法身分**，缺一不可，從不默默交付：
   - **診斷實驗**：明確標註，用來驗證某個假設（「若把 X 關掉症狀消失，原因就在 X」），驗完拆掉。
   - **使用者明示接受**：原因在改不了的地方（第三方、上游、硬體）時，由使用者決定；交付時附上「為什麼不能根治」一句話、根治待辦（追蹤到哪裡）。少任何一樣就不算合法。
5. **回報寫「恢復了什麼」**，不是「問題不見了」。commit 訊息寫原因與恢復的不變量，讓下一個讀碼的人知道為什麼是這樣修。

## 例（產業中性，僅為例）

訂單在付款完成後偶爾顯示「待付款」。

- **workaround**：付款回呼後多等兩秒再查一次狀態。症狀少了，原因還在。
- **根治**：先說原因——「不變量是『訂單狀態只由付款結果單向推進』，而這裡有兩條路徑各自寫入狀態，後寫的覆蓋先寫的」。修在寫入處：狀態只准由一條路徑推進，另一條只讀。回報寫「恢復了狀態單向推進的不變量」。

## 不做什麼

- 不管怎麼找原因、怎麼設計假設與儀器（`diagnosing-bugs`）。
- 不管要不要修、要不要全修（`reproducing` 與使用者）。
- 不管模組怎麼切、依賴怎麼擺（`architecture-governance`）。
